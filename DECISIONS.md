## 2026-08-30 — commitmentHash / canonicalizeCommitmentPayload exported as public API

- **Assumption:** `ASSUMPTIONS.md` — "commitmentHash / canonicalizeCommitmentPayload exported as public API in Phase 1" (originally logged during Phase 1 of the RFC-MACP-0013 plan; resolved once already at the PR #45 ship gate, which narrowed the barrel export).
- **Recommending agent:** Fable (public API contract = genuine one-way door under semver).
- **Recommendation:** CONFIRM. `package.json`'s `exports` map (`"."` and `"./package.json"` only) already blocks external deep-imports of `canonicalizeCommitmentPayload` — it's more private than the assumption's own "reachable via deep import" caveat suggested, so the ship-gate split (barrel-export `commitmentHash` only) is the strongest reversible starting point. Cross-SDK symmetry with `macp-sdk-python` (which keeps its `canonical_projection` equivalent fully internal) is the right goal: exporting `canonicalizeCommitmentPayload` later is a purely additive minor; exporting now and retracting is a breaking change. Non-blocking follow-up: no compile-time frozen-field-set exhaustiveness guard on `CommitmentPayload` (vs. python-sdk's runtime `_check_frozen_field_set`) — cheap (~3 lines), doesn't change API or runtime behavior, tracked separately.
- **My verdict:** Confirm as-is.
- **Resulting status:** `CONFIRMED (2026-08-30)`. Follow-up: [#47](https://github.com/multiagentcoordinationprotocol/macp-sdk-typescript/issues/47) opened for the frozen-field-set exhaustiveness guard (non-blocking, no shipping impact).

## 2026-08-30 — supersedes: null / non-object collides with a legitimate empty-string CommitmentRef

- **Assumption:** `ASSUMPTIONS.md` — "supersedes: null / non-object collides with a legitimate empty-string CommitmentRef" (Phase 1, D3; residual inconsistency between the hasher's `!== undefined` check and the builder's truthy check, flagged by the Phase 2 verifier and carried forward unfixed to this reconcile pass).
- **Recommending agent:** Opus (low blast radius, internal defensive-coercion edge case).
- **Recommendation:** CHANGE. `buildCommitmentPayload`'s `if (input.supersedes)` truthy check silently dropped `supersedes: null` instead of validating/rejecting it — a real (if narrow) "same intent, different hash" trap between the builder path and the hasher path, and inconsistent with the builder's own established behavior of throwing on a malformed `commitmentHash` string. Recommended fix: treat any non-`undefined` `supersedes` as present, throw `MacpSessionError` on `null`/non-object before calling `validateCommitmentHash`, add a unit test for `supersedes: null`.
- **My verdict:** Change per recommendation.
- **Resulting status:** `CHANGED (2026-08-30)` — fix applied directly in this reconcile pass. `src/envelope.ts`'s `buildCommitmentPayload` now checks `input.supersedes !== undefined`, then throws `MacpSessionError` if the value isn't a non-null object, before validating the hash. Unit tests added to `tests/unit/envelope.test.ts` covering `null`, a non-object primitive, a bigint, an array, and an empty object. Full regression: 687 passed / 7 skipped (32 files), coverage unaffected vs floors 94/88/90/94. Does not close the hasher-side `supersedes: null` / empty-string-ref collision in `commitmentHash()` itself — that stays open by design (D3); see the ASSUMPTIONS.md entry's resolution note. A related but distinct bug was found during verification and filed separately, not fixed here: `if (someOptionalField)` truthy-check guards on `sessionId` in `base-session.ts`/`decision.ts`/`proposal.ts`/`task.ts`/`handoff.ts`/`quorum.ts` let an empty-string `sessionId` bypass `validateSessionId` entirely (worse than this bug — an invalid id reaches the wire instead of being dropped). Filed as [#48](https://github.com/multiagentcoordinationprotocol/macp-sdk-typescript/issues/48).

## 2026-08-31 — Issue #55 (first vote stands): observability mechanism

- **Assumption/decision point:** how a projection surfaces a discarded duplicate `Vote`/ballot to a caller, decided during planning (`plans/rfc-0007-first-vote-stands.md`, "Settled decisions") rather than left as an `ASSUMPTIONS.md` entry, because the plan froze it cross-SDK before Phase 3 landed.
- **Options considered:** (a) a caller-supplied callback invoked on every discarded duplicate; (b) a strict mode that throws on the first cardinality violation; (c) changing `applyEnvelope`'s return type to carry a result/diagnostic instead of `void`; (d) recorded diagnostics — a typed `anomalies` array per projection, populated in application order, plus a non-contractual `logger.warn` at record time.
- **Chose:** (d). A callback forces every caller — including the many call sites that apply envelopes in a loop with no interest in anomalies — to either supply a no-op or thread one through. A strict mode changes `applyEnvelope`'s failure behavior for a projection whose entire job, per the "accepted-only input contract" (Phase 1), is to reconstruct history without an authority to reject anything; throwing would make the projection more strict than the runtime it is reconstructing. Changing the return type breaks all six existing call sites for every consumer, in-tree and out, for a signal most callers will never read. Recorded diagnostics cost nothing on the happy path, are inspectable after the fact (`projection.anomalies`, `projection.hasAnomalies`), and match `macp-sdk-python`'s independently-converged choice — the two SDKs arrived at the same shape without coordinating on this specific point first, which was treated as corroboration, not coincidence.
- **Cross-SDK contract:** the `ProjectionAnomaly` record is frozen at seven fields (`kind`, `mode`, `messageType`, `messageId`, `sender`, `subjectId`, `detail`) — deliberately not the full `Envelope`, since the envelope stays recoverable via `messageId` lookup in `transcript`, and seven scalars are a far lighter permanent commitment than a protobuf type in a public diagnostic record. Enforced by a compile-time frozen-field-set guard in `src/projections/base.ts` (`_ProjectionAnomalyFieldSetIsFrozen`), the same shape as the existing `CommitmentPayload` guard (issue #47).
- **The log half is explicitly non-contractual.** `logger.warn` may differ per SDK (level, message shape, whether it fires at all under a given log-level config); only the `anomalies` array is the canonical, cross-SDK-agreed semantic. Stated in both the field's docblock and `docs/api/projections.md` so a future refactor of the log call is understood as free, while touching the array is not.
- **Blast radius if wrong:** Low and reversible — this is a new, additive surface with no prior consumers. If a callback or strict mode turns out to be needed later, it can be added alongside `anomalies` without removing it.

## 2026-08-31 — Issue #55 (first vote stands): `message_id` dedup gates `transcript`

- **Decision:** A redelivered envelope (same `message_id` as one already applied) is absorbed as a non-event by all six `applyEnvelope` entry points: not appended to `transcript`, not passed to the mode-specific `switch`, logged at `debug` (not `warn`) since redelivery is architecturally expected under MACP's at-least-once delivery (RFC-MACP-0001 §8) rather than an anomaly.
- **Normative basis:** RFC-MACP-0006 §3.2 Redelivery, added to the spec (v1.4.0-draft) after this plan's baseline and confirmed against the runtime: on a duplicate `message_id`, `process_message` returns `Precheck::Duplicate` (`macp-runtime/src/runtime.rs:635-640`) **before** `log_store.append` and before `publish_accepted_envelope`. A duplicate never enters accepted history, and `transcript` is defined as a reconstruction of accepted history, so it must exclude duplicates by the same rule the runtime already enforces.
- **Counter-argument, held and explicitly overridden:** a consumer treating `transcript` as an exact receipt of every envelope handed to `applyEnvelope` would now observe silent drops it did not ask for. Overridden for two reasons: (a) `applyEnvelope` already silently drops envelopes for other modes (the mode-check at the top of every entry point discards a mismatched `envelope.mode` with no signal) — "an exact receipt of everything handed in" was never the contract, dedup is not introducing a new kind of silent drop, only a second trigger for an existing one; (b) a consumer relying on that non-existent receipt guarantee is, in this SDK's own `Participant` topology (see the shared-projection-instance assumption in `ASSUMPTIONS.md`), already receiving the initiator's own envelope twice via the ACK-apply-then-replay path — its data was corrupted by that echo before this decision, not after it.
- **Placement is load-bearing, not incidental:** the dedup guard sits in `BaseProjection.applyEnvelope` *before* `this.transcript.push(...)` and before the mode-specific switch. Moving it after `transcript.push` was verified (via a mutation test) to make `transcript.length` assertions fail while accumulate-site assertions (`evaluations`, etc.) still pass — proving the guard's position, not just its existence, is what makes the seven accumulate-on-apply sites (Decision `evaluations`/`objections`, Proposal `accepts`/`rejections`, Task `updates`/`completions`/`failures`) idempotent under redelivery.
- **Blast radius if wrong:** Confined to callers who built tooling around `transcript` including redeliveries, which the codebase's own docs and tests never depicted as intended usage (swept — see the plan's "Docs sweep" note). Reversible: the guard is a single early-return per entry point.

## 2026-08-31 — Issue #55 (first vote stands): semver — `feat(projections)!` landing `0.7.1 → 0.8.0`

- **Decision:** Ship as `feat(projections)!:` with an explicit `BREAKING CHANGE:` footer, per `ASSUMPTIONS.md`'s "Semver marker" entry. Under this repo's `bump-minor-pre-major: true` (`release-please-config.json`), both a plain `feat:` and a `feat!:` land the same version bump — `0.7.1 → 0.8.0` — so the `!` and footer cost nothing in version arithmetic.
- **Why mark it breaking anyway:** `DecisionProjection.voteTotals()`/`majorityWinner()`/`voteRatio()` and the seven affected of `QuorumProjection`'s nine public derived methods (`approvalCount`, `rejectionCount`, `abstentionCount`, `hasQuorum`, `remainingVotesNeeded`, `commitmentReady`, `isThresholdUnreachable` — `threshold()` and `votedSenders()` are unaffected) now return different values for a transcript containing a second distinct vote/ballot from one sender — exactly the case two shipped doc sections (`docs/modes/quorum.md`'s deleted "Vote Override" section, `docs/modes/decision.md`'s "Vote Deduplication" section) told readers to rely on. A loud changelog signal reaches precisely the people those sections misled. A plain `feat:` would have been technically defensible (the analysis pass that recommended it was correct that only spec-non-conforming transcripts are affected) but under-describes the change's practical impact to anyone who followed the now-deleted guidance.
- **Blast radius if wrong:** Cosmetic — an over-loud changelog entry on a 0.x package, reversible by editing release notes after the fact; the version number is identical either way under `bump-minor-pre-major`.

## 2026-08-31 — Issue #55 (first vote stands): retiring two intent-documenting tests by deletion, not edit

- **Decision:** `tests/unit/projections/decision.test.ts`'s `'deduplicates votes by sender per proposal'` (asserted `totals['p1'] === 1` with the comment `// latest vote wins`) and `tests/unit/projections/quorum.test.ts`'s `'same sender voting again overwrites previous vote'` (asserted `hasQuorum('r1') === true` under `requiredApprovals: 1` from a single sender's reject-then-approve) were both **deleted outright**, each replaced by a new, differently-named test asserting the opposite outcome, rather than edited in place to flip their assertions.
- **Why deletion beats editing:** both tests were not incidental — they had comments and names stating the old behavior was the *intended* rule, not an oversight being fixed. Editing the assertions in place would leave `git blame`/`git log -S` on the old test name landing on this same commit, making it look like the test's *name* was always paired with today's assertions. Deleting and adding a new, distinctly-named test means `git log -S 'deduplicates votes by sender per proposal'` and `git log -S 'same sender voting again overwrites previous vote'` land exactly on the commit that retired the intent they documented — a reviewer or future archaeologist tracing either string finds the retirement, not a quietly modified test that erases its own history.
- **Highest-consequence case:** the retired Quorum test, under `requiredApprovals: 1`, had a single sender's duplicate ballot (reject-then-approve) reported `hasQuorum() === true` — a duplicate could **fabricate quorum**, reporting an approval threshold met when the only voter's binding first ballot was a rejection. This was pinned as *correct* behavior by the test being retired.
- **Blast radius if wrong:** None beyond commit-history readability — the deletion is purely presentational; the replacement tests carry the same (inverted) assertions either way.
